# Тестирование Sprite Cutter

Это руководство описывает запуск, устройство и сопровождение тестов.
Контракты реализации и решения, уточняющие ТЗ, собраны в
[TDD-контрактах](tdd.md). Требования приложения — в [ТЗ MVP](../mvp-spec.md).

## Текущее состояние

Актуальный полный прогон после очистки дублирующих сценариев: **141 Vitest и 16 Playwright**,
все проверки проходят. Числа ниже для MVP и интеграции отражают историю этапов.

Тесты написаны до реализации MVP; сейчас основной сценарий реализован. Зафиксированный первый прогон содержит
48 тестов: 3 проверки тестовой инфраструктуры проходят, 45 проверок приложения
падают с `MVP not implemented: ...`. Это исходная точка RED, а не требование
сохранять ошибки после реализации. Пропущенных тестов нет.

После завершения RED-фазы временные загрузчики контрактов и отдельные тесты самих
моков удалены. Текущие тесты напрямую импортируют публичный код приложения и
проходят без `skip`, `todo`, `test.fails` и подмены проверяемых модулей.

## Подготовка и команды

Запускайте команды из корня проекта после `pnpm install`.

| Команда                                             | Назначение                                   |
| --------------------------------------------------- | -------------------------------------------- |
| `pnpm test`                                         | Наблюдение за изменениями и повторный запуск |
| `pnpm test:run`                                     | Весь набор, один запуск; подходит для CI     |
| `pnpm test:coverage`                                | Весь набор с покрытием и проверкой порогов   |
| `pnpm exec vitest run src/test/mvp/grid.test.ts`    | Расчёт сетки                                 |
| `pnpm exec vitest run src/test/mvp/export.test.ts`  | Нарезка и кодирование                        |
| `pnpm exec vitest run src/test/mvp/editor.test.tsx` | Сценарии через интерфейс                     |
| `pnpm exec vitest run -t 'CSS-scaled canvas'`       | Выбор теста по части названия                |
| `pnpm typecheck`                                    | Проверка TypeScript приложения и тестов      |
| `pnpm lint`                                         | Проверка Oxlint, включая правила Vitest      |

Для подробного вывода:

```sh
pnpm exec vitest run --reporter=verbose
```

Для машиночитаемого отчёта:

```sh
pnpm exec vitest run --reporter=json --outputFile=/tmp/sprite-cutter-tests.json
```

Ненулевой код выхода означает неуспешный прогон. На RED-этапе это ожидаемо;
после реализации такой результат должен блокировать принятие изменений.
По завершении исходного этапа MVP набор содержал 52 теста Vitest. После реализации
повторяющиеся DOM-комбинации перенесены в прямые доменные проверки, а отдельные
тесты тестовой инфраструктуры удалены. Браузерные сценарии остаются в
`tests/browser/editor.spec.ts`.

Покрытие считает `@vitest/coverage-v8`: `pnpm test:coverage` выводит таблицу,
сохраняет HTML-отчёт в `coverage/` и проверяет глобальные пороги из
`vitest.config.ts` — 90% инструкций, 85% ветвей, 95% функций, 94% строк.
Недостижение порога завершает прогон с ненулевым кодом. Пороги держатся ниже
достигнутых значений: они ловят падение покрытия, а не требуют ровной цифры.
Число тестов по-прежнему не является процентом покрытия.

## CI: GitHub Actions

Workflow [CI](../../.github/workflows/ci.yml) запускается при каждом push и pull request.
Один job `Quality checks` на Ubuntu 24.04 выполняет проверки последовательно;
ошибка любого шага останавливает дальнейшие проверки.

Node.js берётся из `.nvmrc` (22.19.0), pnpm — из поля `packageManager`
в `package.json` (12.3.4). При обновлении версий меняйте эти файлы:
workflow читает их напрямую. `pnpm install --frozen-lockfile` запрещает
неявное обновление `pnpm-lock.yaml`; зависимости кэшируются по lockfile.
Lockfile также содержит служебную секцию pnpm с зафиксированной версией
самого менеджера пакетов; её нужно сохранять вместе с зависимостями приложения.
Husky отключён через `HUSKY=0`, поскольку проверки в CI запускаются отдельными шагами.

Последовательность для локального воспроизведения на тех же версиях Node.js и pnpm:

```sh
pnpm install --frozen-lockfile
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test:coverage
pnpm build
pnpm exec playwright install --with-deps chromium
CI=true pnpm test:e2e
```

Установка системных зависимостей Chromium на Linux может потребовать `sudo`.
В CI используется браузер, соответствующий установленной версии Playwright;
`PLAYWRIGHT_CHROMIUM_EXECUTABLE` там не задаётся. `CI=true` запрещает
повторно использовать уже запущенный dev-сервер: Playwright поднимает свой.
Проверка TypeScript включает отдельный domain-проект без DOM.

При падении браузерных тестов каталог `test-results/` с трассировками сохраняется
в артефакте `playwright-failure-artifacts` на 7 дней. Логи всех шагов доступны
во вкладке Actions репозитория. Повторный push в ту же ветку отменяет устаревший
прогон; ограничение времени job — 20 минут. Workflow проверяет качество,
публикация приложения не настроена.

## Что проверяется

### Сетка: `grid.test.ts`

Проверяются размер массива, начальный и последний кадры, кадр с номером 11,
уникальность ID, отсутствие выделения при генерации и независимость объектов
между вызовами. Прямоугольная сетка 96×40 с кадром 32×20 сравнивается целиком
с явно заданными ожидаемыми объектами.

Граничные случаи: изображение равно кадру, кадр больше изображения по одной
или обеим осям, неполные края, нулевые, отрицательные, дробные размеры,
`NaN` и `Infinity`. Для изображения 4096×4096 и кадра 32×32 проверяется
количество 16384, но не время отрисовки интерфейса.

### Экспорт: `export.test.ts`

Проверяются размеры выходного canvas и параметры `drawImage`:

```text
source:      x=64, y=32, width=32, height=32
 destination: x=0,  y=0,  width=32, height=32
```

Отдельный случай использует прямоугольный кадр 48×20. Проверяются запрос
`toBlob` с MIME `image/png`, возвращённый Blob и отклонение Promise при
отсутствии 2D-контекста или результате `toBlob(null)`.

### Интерфейс: `editor.test.tsx`

Сценарии работают через React Testing Library: загрузка файла, ввод размеров,
клики по canvas и нажатие кнопки экспорта. Проверяются:

- пустое состояние, PNG/JPEG/WebP, метаданные, отмена выбора файла;
- неподдерживаемый тип и ошибка загрузки изображения;
- счётчики сетки и вызовы рисования;
- выбор нескольких кадров, повторный клик, preview;
- пересчёт указателя при CSS-масштабе, границы ячеек и неполные края;
- валидация обоих размеров и восстановление после исправления;
- сброс выбора при изменении сетки и замене изображения;
- отдельные скачивания выбранных кадров, имена, MIME и освобождение URL;
- ошибка экспорта и отсутствие скачивания повреждённого результата.

Точные доступные имена элементов, подписи счётчиков и сигнатуры функций
описаны в [контрактах](tdd.md#контракты-реализации).

## Моки и фикстуры

`installBrowser()` устанавливается заново перед тестом. Он возвращает
фабрику `file`, контексты canvas, журнал скачиваний, активные URL и spies.

| API                            | Поведение мока                                                                                             |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `Image`                        | Создаёт HTMLImageElement; присваивание `src` асинхронно вызывает load/error и задаёт размеры из метаданных |
| `URL.createObjectURL`          | Выдаёт уникальный локальный URL и сохраняет связь с Blob                                                   |
| `URL.revokeObjectURL`          | Удаляет URL из реестра                                                                                     |
| `canvas.getContext('2d')`      | Возвращает отдельный набор spies для каждого canvas                                                        |
| `canvas.toBlob`                | Асинхронно возвращает условный Blob с MIME image/png                                                       |
| `anchor.click`                 | Сохраняет имя и Blob скачивания до освобождения URL                                                        |
| `fetch`, `XMLHttpRequest.send` | Выбрасывают ошибку при попытке отправки данных                                                             |

Примеры использования внутри теста с установленными хуками очистки:

```ts
const browser = installBrowser()
const validFile = browser.file() // player.png, 256×128
const brokenFile = browser.file(undefined, true)
browser.toBlob.mockImplementation((callback) => callback(null))
```

`validFile` и `brokenFile` — файлы с условными байтами. Мок Image не декодирует
PNG/JPEG/WebP. Эти проверки доказывают обработку событий и метаданных,
а не поддержку кодека реальным браузером.

Реальные PNG хранятся отдельно:

| Файл         | Размер  | Ожидание при кадре 32×32                                   |
| ------------ | ------- | ---------------------------------------------------------- |
| `player.png` | 256×128 | 8 колонок, 4 строки, 32 кадра                              |
| `uneven.png` | 100×100 | 3 колонки, 3 строки, 9 кадров; полосы по 4 px игнорируются |
| `enemy.png`  | 64×32   | 2 колонки, 1 строка, 2 кадра                               |

В PNG ячейки окрашены по-разному, первый пиксель каждой ячейки прозрачен.
Для кадра с `displayNumber: 11` исходный прямоугольник — `(64, 32, 32, 32)`, имя экспорта
по принятому контракту — `frame_011.png`. Ожидаемые пиксели берутся из самого
исходного PNG: оракул `comparePngCrop` в `tests/browser/support.ts` декодирует его
в Chromium независимо от кода приложения и сравнивает с экспортом побайтово.
Вычислять ожидания проверяемой функцией нельзя.

## Порядок реализации по TDD

1. Убедиться, что текущий набор зелёный: `pnpm test:run` до внесения изменений.
2. Выбрать один сценарий и прочитать его ожидания и соответствующее требование ТЗ.
3. Запустить сценарий и убедиться, что причина RED соответствует отсутствующему поведению.
4. Реализовать минимальное необходимое поведение в рабочем коде.
5. Получить GREEN для сценария, затем запустить весь соответствующий файл.
6. Выполнить рефакторинг и повторить проверки затронутого поведения.
7. Перед завершением MVP запустить весь набор, TypeScript и линтер, затем пройти сценарий в браузере.

Рекомендуемый порядок: генерация кадров → загрузка и отображение → сетка и
выбор → preview → экспорт → замена изображения и обработка ошибок.

Во время исходной RED-фазы временные контракты загружали ещё не существовавшие
модули через `import.meta.glob`. После реализации они удалены: проверки напрямую
импортируют `generateFrames`, `exportFrame`, `exportFramesZip` и `App` через
публичные API FSD.

## Добавление тестов

Используйте названия, описывающие действие и наблюдаемый результат. Для повторяющихся
граничных значений подходит `test.each`. Ожидания задавайте независимыми числами
или эталонными объектами, а не результатом той же функции, которую проверяете.

Для DOM используйте роли и доступные имена. Для действий пользователя —
`userEvent`; `fireEvent` нужен для точных координат canvas и намеренного обхода
фильтра файлов. Асинхронные изменения проверяйте через `findBy*` и `waitFor`,
без произвольных задержек. Не помещайте действие пользователя внутрь `waitFor`:
оно может выполниться несколько раз.

В тестах с `installBrowser()` сохраняйте изоляцию: размонтируйте React-дерево
до восстановления API, вызовите `vi.unstubAllGlobals()` и `vi.restoreAllMocks()`
после теста. Глобальный setup также выполняет DOM cleanup. Не используйте
совместно изменяемые объекты кадров между сценариями.

## Диагностика ошибок

| Сообщение или симптом                 | Что проверить                                                         |
| ------------------------------------- | --------------------------------------------------------------------- |
| Не найден элемент по роли/имени       | Связь label с полем, aria-label canvas, видимость и подписи           |
| `Canvas did not request a 2D context` | Получение контекста и момент запуска эффекта рисования                |
| `Images must stay local`              | Непредусмотренный fetch/XHR в проверяемом сценарии                    |
| После теста остались URL              | Очистку при ошибке, замене изображения, скачивании и unmount          |
| Таймаут ожидания изображения          | Подписку load/error до установки src и обработку асинхронного события |

## Проверки в настоящем браузере

jsdom не рисует изображение и не кодирует PNG. Наличие вызова рисования ещё
не доказывает визуально правильную сетку или подсветку. Текущие проверки также
не запускают `src/main.tsx`, не измеряют адаптивность, FPS или полноту сетевой
изоляции. Браузерный E2E-раннер Playwright настроен отдельно от Vitest.

Для ручной приёмки:

1. Запустить приложение через Vite и загрузить реальный `player.png`.
2. Задать 32×32, проверить сетку и выбрать кадры с номерами 1 и 11.
3. Проверить preview, снятие выделения и счётчик.
4. Скачать PNG и декодировать результаты: размер каждого — 32×32, а RGBA кадра
   с номером 11 совпадают с областью `(64, 32, 32, 32)` исходного `player.png`.
5. Убедиться, что прозрачность сохранена, а линии сетки и выделение не попали в экспорт.
6. Проверить реальные JPEG/WebP, замену на `enemy.png` и остатки у `uneven.png`.
7. Проверить несколько скачиваний с учётом разрешений браузера, ширину окна
   1024px и отзывчивость на изображении 4096×4096.

Результаты автоматизированного браузерного прогона фиксируются отдельно; ручная
проверка настроек скачивания зависит от браузера пользователя.

## Playwright: настоящие PNG

```sh
pnpm exec playwright install chromium
pnpm test:e2e
```

Можно использовать уже установленный Chrome:

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/google-chrome pnpm test:e2e
```

Playwright запускает Vite и проверяет приложение в Chromium. Тесты исключены
из поиска Vitest и проверяются TypeScript через tsconfig.e2e.json.

Проверки: реальные player.png и test.png, размеры и пиксели preview/экспорта,
несколько отдельных скачиваний, клавиатура, замена файла, ширина 1024px,
декодирование JPEG/WebP и выбор на PNG 4096×4096. Полный RGBA-массив нарезанного
кадра сравнивается с исходной областью после независимого декодирования.
Для test.png (1774×887) явно задана сетка 32×32: 55 колонок, 27 строк, 1485 кадров.
Тест берёт область (224, 64, 32, 32), `displayNumber: 118`, имя frame_118.png.
Это проверка нарезки, а не автоматический поиск границ персонажей на листе.

При падении Playwright автоматически сохраняет скриншот и трассу в
`test-results/`; успешные сценарии не создают диагностические изображения.

## Проверки границы интеграции

`src/test/integration/editor.test.tsx` проходит upload → selection → preview →
export отдельно для публичного SpriteEditor и standalone App без подмены компонентов.
`src/test/integration/domain.test.ts` запускает domain в Node без document и
проверяет точную форму типов результата через expectTypeOf. Проверки типов
выполняются командой typecheck; Vitest не заменяет компилятор TypeScript.
Дополнительный tsconfig.domain.json компилирует domain без DOM ambient types.

После подготовки Forge2D: 56 тестов Vitest; 4 существующих Playwright-сценария
сохраняются. Это результаты этапа интеграции; v0.2 реализован следующим этапом.

Реализация и тесты: [v0.2 — контракты и история TDD](v02.md).
На этапе v0.2: 113 Vitest и 6 Playwright, все GREEN.

- отсутствие частичного ZIP при ошибке, повторный экспорт и удаление последнего кадра.

`src/test/manual/collection-zip.test.ts` проверяет совпадающие, пустые,
зарезервированные имена, символы пути и кириллицу. Независимый ZIP-reader
проверяет записи и CRC; production-код архивирования не используется для чтения.

`tests/browser/collection.spec.ts` обводит персонажей на реальном `test.png`,
добавляет три кадра, переименовывает их одинаково, удаляет третий и скачивает ZIP.
Проверяются два уникальных имени, размеры и все пиксели обоих PNG после
независимого декодирования через общий пиксельный оракул.

```sh
pnpm exec vitest run src/test/manual
pnpm exec playwright test tests/browser/collection.spec.ts
```
