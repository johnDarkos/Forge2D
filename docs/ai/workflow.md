# Рабочий процесс

Этот файл обязателен для следующих сессий разработки. Он задаёт порядок работы, а не
заменяет техническую документацию.

## Перед началом

1. Прочитать `context.md`, `architecture.md` и `current-milestone.md`.
2. Проверить `git status --short --branch`, текущий HEAD и связь с `main`/remote.
3. Просмотреть релевантные части `../project.md` и `../Forge2D-Architecture-v0.1.md`.
4. Проверить существующие реализации и тесты через `rg`; не создавать параллельный контракт.
5. Если рабочее дерево содержит чужие изменения, сохранить и учесть их, не откатывать.

## Реализация

1. Выбрать один проверяемый срез текущего milestone.
2. Для нового поведения сначала написать тест и получить осмысленный RED.
3. Реализовать минимальный контракт, затем обработать ошибки и lifecycle.
4. Использовать существующие публичные границы между Core, Runtime, Editor и Sprite Editor.
5. Не привязывать Core/Runtime к DOM, React или выбранному renderer backend без отдельного
   архитектурного решения.
6. После зелёных focused-тестов запускать общий набор только один раз, если дальнейшие
   изменения не требуют повтора.

Тесты должны проверять поведение и реальные границы. Не добавлять перебор DOM-комбинаций,
тесты самих mock или копии одного оракула. Пиксели, PNG/ZIP и browser lifecycle проверяются
Playwright на реальных данных.

## Обязательные проверки

Для завершённого этапа:

```sh
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test:coverage
pnpm build
PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/google-chrome pnpm test:e2e
```

`pnpm install --frozen-lockfile` дополнительно запускается после изменения workspace или
lockfile. Для локальной проверки конкретного пакета сначала используются его `test` и
`typecheck` scripts.

## Документация после работы

Перед завершением каждой задачи проверить и при необходимости обновить:

- `current-milestone.md` — прогресс чекбоксов, следующий шаг, новый HEAD и блокеры;
- `context.md` — только если изменились возможности, baseline или состояние roadmap;
- `architecture.md` — только если появился или изменился контракт, зависимость либо инвариант;
- `../project.md` — подробное фактическое поведение, тестовый baseline и roadmap;
- `../Forge2D-Architecture-v0.1.md` — только для утверждённого изменения целевой архитектуры.

Не копировать большие разделы между документами. `docs/ai/` должен оставаться коротким
оперативным индексом, а `project.md` — подробной документацией реализации.

## Git

- Один коммит должен представлять один законченный смысловой шаг.
- Исправление предыдущего этапа отделяется от реализации следующего.
- Перед коммитом проверить staged diff и `git diff --cached --check`.
- Не переписывать опубликованную историю и не смешивать незавершённый milestone с `main`.
- Feature-ветка должна оставаться линейно основанной на актуальном `main`; расхождение
  `0 N` означает нормальное опережение feature-ветки, а не конфликт.
- Push и merge выполняются по явной команде пользователя.

## Definition of Done

Работа завершена, когда код и тесты реализуют согласованный контракт, quality pipeline
проходит, рабочее дерево содержит только ожидаемые изменения, а `docs/ai/` и основная
документация описывают фактическое состояние. В итоговом сообщении указываются результат,
проверки, коммит/состояние рабочей ветки и следующий конкретный шаг.
